## 二、问题一：macOS 打包安装后 Spotlight/启动台搜索不到应用

### 1. 故障现象
在 macOS 上将打包好的 `HQ Network Debugger.app` 安装拖入 `/Applications` 后，使用系统快捷键 `Cmd + 空格`（Spotlight 聚焦搜索）输入 `HQ` 或 `HQ Network Debugger`，无法检索出该应用程序。

### 2. 排查过程与根本原因

#### ❌ 排除假说：应用名称包含空格导致
- 系统自带应用如 `QuickTime Player.app`，第三方如 `Google Chrome.app`、`DeepSeek Harness.app`、`Clash Verge.app` 均带空格且正常索引。经重命名测试后确认与名称空格无关。

#### 🔍 真实根因 1：App Bundle 代码签名不完整（Gatekeeper 抑制机制）
- 使用 macOS 安全评估工具 `spctl` 对原安装包进行检测：
  ```bash
  spctl -a -vvv "/Applications/HQ Network Debugger.app"
  # 输出: code has no resources but signature indicates they must be present (exit code 1)
  ```
- **原因**：之前的构建仅对底层 Rust 可执行程序进行了签名，但 Tauri 打包外层注入的 `Contents/Resources/backend/` 时，未对外层 App Bundle 进行递归数字密封签名。macOS 判定 Bundle 损坏，Gatekeeper 将该应用静默列入搜索抑制名单。

#### 🔍 真实根因 2：macOS 聚焦索引守护进程处于假死停滞状态
- 终端检索磁盘索引状态：
  ```bash
  mdutil -s -a
  # 输出: /System/Volumes/Data: Error: unknown indexing state.
  ```
- 检索全盘最近 7 天所有文件的 Spotlight 索引记录：
  ```bash
  mdfind 'kMDItemFSContentChangeDate >= $time.today(-7)'
  # 输出: 0 条
  ```
- 检索近期安装的其它主流应用：
  - 10月27日安装的 `ChatGPT.app` 👉 搜不到
  - 10月26日更新的 `Antigravity.app` 👉 搜不到
  - 10月20日更新的 `Visual Studio Code.app` 👉 搜不到
- **结论**：系统级 Spotlight 数据库自 10 月 19 日后由于磁盘索引锁死已停止自动更新。

### 3. 修复措施

1. **配置 Tauri 自动密封代码签名**：
   在 `src-tauri/tauri.conf.json` 中配置：
   ```json
   "bundle": {
     "active": true,
     "targets": ["app", "dmg"],
     "macOS": {
       "signingIdentity": "-"
     }
   }
   ```
2. **构建结果验证**：
   ```bash
   codesign --verify --deep --strict --verbose=2 "dist/方案A-Tauri/HQ Network Debugger.app"
   # 输出: valid on disk, satisfies its Designated Requirement
   ```
3. **提供官方级 1 分钟索引唤醒方案**：
   - 打开「系统设置」->「Siri 与聚焦」-> 点击右下角「聚焦隐私...」。
   - 点击 `+` 将「应用程序」文件夹（或整个硬盘）添加，点击完成。
   - 再次打开「聚焦隐私...」，选中刚刚添加的项，点击 `-` 移除，点击完成。
   - 系统将立即重新扫描 `/Applications`，彻底恢复包括本应用在内的全部搜索结果。

## 三、问题二：Map Local (Mock) 规则在相同 API 再次请求时失效

### 1. 故障现象
在抓包界面对某个请求点击「⚡ Map Local (以此数据 Mock)」并保存后，第 1 次或者后续重复请求相同 API 时，请求未命中 Mock 规则，列表没有展示 `⚡ MOCK` 标识，响应内容依然透传自真实外网服务器。

### 2. 深度源码排查与根因分析

通过分析实际抓包记录 `POST https://interface-test.voghion.com/cms/content-dispatch/search/searchContent`，并在 Node 环境中针对 `Mockttp` 核心匹配机制进行断点与单测，定位到三个相互叠加的核心缺陷：

#### 🔍 根因 1：Mockttp 自定义规则默认为单次完成（`once`）模式
- 翻阅 `node_modules/mockttp/dist/rules/requests/request-rule.js` 与 `base-rule-builder.js`：
  ```javascript
  isComplete() {
      if (this.completionChecker) {
          return this.completionChecker.isComplete(this.requestCount);
      } else if (this.requestCount === 0) {
          return false; // 请求数为 0 时，规则视为未完成
      } else {
          return null;  // 请求数 >= 1 时，状态变为 null（可能已完成）
      }
  }
  ```
- 当未调用 `.always()` 显式声明时，规则在被第 1 次请求命中后，其状态立即从 `false` 变成 `null`。在后续请求匹配中，Mockttp 会跳过该规则去寻找其他规则。

#### 🔍 根因 2：兜底透传规则的优先级竞争
- 原 `src/proxy-server.js` 中的透传策略为：
  ```javascript
  await this.server.forAnyRequest().thenPassThrough();
  ```
  `forAnyRequest()` 的优先级为 `RulePriority.DEFAULT (1)`，与自定义 Mock 规则完全相同。当自定义规则在第 1 次执行后变为 `null` 状态，后续请求在同级优先级下优先命中了兜底透传规则，导致全部直接放行至外网。

#### 🔍 根因 3：请求带有动态 Query 防缓存时间戳
- 客户端或移动端常在 URL 后拼接随机防缓存参数（如 `?_t=173010...`）。原精确匹配采用全字符串对比，由于规则 Pattern 未包含随机参数，导致严格匹配失败。

### 3. 修复代码实现

在 [`src/proxy-server.js`](file:///Users/edy/Desktop/1hhq/1AItools/HqNetworkPacketCapture/src/proxy-server.js) 中完成加固：

```javascript
// 1. 显式添加 .always()，确保该 Mock 规则无限次持久生效
builder = builder.matching(matchPredicate).always();

// 2. 将兜底透传改为 forUnmatchedRequest()，设定为 FALLBACK 降级优先级 (0)
await this.server.forUnmatchedRequest().thenPassThrough();

// 3. 智能兼容动态 Query 参数
if (!patternHasQuery) {
  const reqUrlBase = reqUrlClean.split('?')[0];
  if (reqUrlBase === cleanPattern) return true;
  if (reqUrlBase.replace(/^https?:\/\//, '') === patternNoProtocol) return true;
  if (req.path && req.path.split('?')[0].replace(/\/+$/, '') === cleanPattern) return true;
}
```

### 4. 自动化回归测试验证
编写 Node.js 模拟真实客户端发起 3 轮连续请求及带参请求实测：
```text
[ProxyServer] 已生效 1 条 Mock 规则，其余请求正常透传
Request 1 mocked: true
Request 2 mocked: true
Request 3 mocked: true
Request with query param mocked: true
```
**结果**：所有请求均稳定命中 Mock 数据，响应头附带 `x-mocked-by: hq-maplocal`。

## 四、问题三：代理底层 ERR_SSL_WRONG_VERSION_NUMBER 异常分析

### 1. 故障日志展示
```text
TLS client hello data not available for TLS connection from ::ffff:10.10.204.104: Can't calculate TLS fingerprint - not a TLS client hello
Unknown TLS error: Error: 80DD99EC01000000:error:0A00010B:SSL routines:tls_validate_record_header:wrong version number:../deps/openssl/openssl/ssl/record/methods/tlsany_meth.c:85:
    at initRead (node:_tls_wrap:511:25)
    code: 'ERR_SSL_WRONG_VERSION_NUMBER'
```

### 2. 技术原理解析
- **来源 IP**：`10.10.204.104` 为连入当前代理的移动端手机设备。
- **错误成因**：
  OpenSSL 在尝试执行 TLS 握手解密时，期望读取到标准的 TLS 握手头（`0x16` 开头）。但实际上读取到了**非 TLS 报文**（如纯文本 HTTP 请求、或移动端 App 的私有 TCP 二进制协议），OpenSSL 将首字节作为协议版本号校验时报错。
- **产生场景**：
  1. **后台 App 私有二进制长连接（最常见）**：手机连接 Wi-Fi 代理后，微信、推送服务（小米/华为推送等）、游戏等会向 443 端口发起隧道连接，通道建立后直接传输自己的私有加密数据（非标准 TLS）。
  2. **端口填错**：将手机 Wi-Fi 代理端口误配成了 Web 管理控制台端口（8899）。
- **结论与影响评估**：
  - **对正常抓包无任何影响**：Mockttp 内核自带异常连接保护机制，该非标准 socket 已被自动重置与关闭。
  - **处理方案**：确保证书安装正常、手机代理端口指向 `8888`，此类由手机后台其他 App 触发的警告日志直接忽略即可。

## 五、技术调研：macOS 跨平台打包 Windows 安装包方案

| 对比维度 | 方案 A (Tauri 架构) | 方案 B (Electron 架构) |
| :--- | :--- | :--- |
| **能否在 Mac 本地直接打包 Windows？** | ❌ **官方不推荐，本地极困难** | ✅ **完全支持，一条命令直出** |
| **核心障碍/实现机制** | 强依赖 Windows 平台的 MSVC 编译工具链、Windows SDK、WebView2 Loader，且内嵌 Node 需要区分 `node.exe` | `electron-builder` 自带跨平台的 Windows 二进制包与 macOS 版 `makensis` 编译工具链 |
| **本地打包命令** | 需配置虚拟机（UTM/Parallels） | `npx electron-builder --win --x64` 即可在 `dist/` 生成 Setup.exe 和绿色免安装 exe |
| **业界工业级最佳解法** | **GitHub Actions CI/CD（强烈推荐）** | 本地直接构建 或 GitHub Actions 自动化构建 |

> **GitHub Actions 实践方案**：  
> 鉴于本项目已托管于 GitHub，未来只需添加 `.github/workflows/build.yml` 工作流文件。开发者在 SourceTree 打 tag（如 `v1.0.0`）推送到 GitHub 时，GitHub 免费提供的云端 Windows 主机会自动拉取代码、执行编译并产出 Windows 安装包，自动挂载到 Release 页面，无需占用本地环境。
